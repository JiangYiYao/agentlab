# 准备和执行实验

用于新实验、增加样本或讨论改法。查看历史、审计和清理直接走各自入口，不重新提一轮实验方案。已经确认的选择和授权继续有效。

## 从改法或现成版本开始

用户要商量优化时，先读相关目录，说明改哪个文件、怎么改、预期改善和可能退步的地方。一次提出一处可核对的改法，让用户修正；改法尚未确定时，先完成讨论，不提前追问启动命令或开跑。用户已指定或授权改法，就继续准备实验。

用户直接要测现成版本时，直接写测试计划，不额外发明改动。只测一个版本也可以，只保留对照组。

## 测试计划

用对照组、实验组1等用户能理解的名字。按已有事实填具体数字；未知处标“待确认”，不能用猜测的次数发起模型调用。

| | 对照组 | 实验组1 |
|---|---|---|
| 内容 | 当前目录或现成版本 | 已确认的改法或另一现成版本 |
| 样本 | N 个用例，各 R 次 | 同样 |
| 本次新执行 | 数字 | 数字 |
| 复用已有执行 | 数字 | 数字 |
| 本次新评分 / 复用评分 | 分别写数量与评分类型 | 分别写数量与评分类型 |

按实际组数增减列。表后写总的新执行次数、裁判形态与调用次数、并发数、判断标准、必须满足的要求及产物位置。并排裁判按跨组批次单独列总数，不能把同一次调用重复记到各组。

有噪声的真实模型或外搜任务，默认建议同一用例至少重复 3 次，或至少 2 个用例各重复 2 次；确定性假命令可以 1×1。用户明确要求先试一次时按他的要求。通常建议并发 2～4；工具、登录或额度有冲突时减少并发，并说明原因。并发指同时运行的试验上限，不保证对照组与实验组成对启动。

用计划确定的 `repetitions`、`max_parallel` 和容纳样本数的 `max_trials` 写配置。默认不设 `wall_clock_s`、`usd`、`tokens`；用户要求设时按 [lifecycle.md](lifecycle.md) 配预留额。增加重复次数时同步更新新执行和裁判次数。

## 裁判与次数

先区分三个量：**被测命令的新执行次数、需要新评分的条目数、实际裁判调用数**。复用执行仍可能需要新评分；不能按“新执行 × LLM 关注点”一律计算。

- `per_trial` 独立审查：每个需要新评的“试验 × LLM 关注点”调用一次。全新实验的 6 次试验、每次 3 条 LLM 分，共 18 次。若复用这 6 次执行但全部换裁判，仍是 18 次；相同口径的缓存分数可复用，不产生调用。
- `compare_case` 并排对比：每个需要新评的“用例 × 执行命令 cell × 重复序号”组调用一次，一次评该组各版本及全部 LLM 关注点。2 个用例、1 个 cell、各重复 3 次，共 6 次，组数和关注点数不再相乘。对照组执行可复用，但更新任一答卷或裁判会重评该组。
- `rescore` 强制重评选中范围的 LLM 分，**新执行为 0，裁判调用可以大于 0**；未变化的脚本测量复用。范围及重复数沿用来源运行，再应用本次筛选。

检查已有运行、筛选范围和输入是否变更后列出计划值。若无法确认缓存命中，写清“最多 K 次，缓存命中后减少”，并按这个上限说明调用范围，不伪造确定值。`run --dry-expand` 只列试验组合，不能据此宣称已经核实缓存命中或裁判次数。中断、环境失败和材料不足也可能减少实际调用；结果按运行记录报告。

有 LLM 分时，说明裁判命令/模型、形态、材料和数量。用户只指定模型时，补充形态提案；已确认的形态沿用。独立审查适合各自评分、观察波动；并排适合同题比较。文本回答看 stdout，文件/数据任务看 `evidence.files`，编码任务看补丁与改后文件，细节见 [coding.md](coding.md)。无 LLM 分写“无”。

能通过退出码、路径、JSON 或文件内容明确验证的要求用脚本，可以作为必须满足项；LLM 用于内容判断，不作为必须通过项。标准按用户需求写，不套某领域清单。

## 开跑前准备

只补缺少的事实：被测目录、已能在本机使用的启动命令、任务输入方式（stdin / 参数 / 文件）和用例材料。不要猜用户使用哪条 CLI。解释器按 SKILL.md 自行准备。

在已有授权内完成可检查的配置和副本；新计划尚未确认时先展示方案，再开跑。不要要求用户填写 YAML。用户已确认范围和标准，直接继续。

1. 默认在 `$AGENTLAB_HOME/experiments/<id>/`，未设则 `~/.agentlab/experiments/<id>/` 准备实验。用户指定位置时采用指定位置；已有同一实验继续使用，同名其他实验另加序号。
2. 按 [contract.md](contract.md) 写 `experiment.yaml`、按关注点分节的 `criteria.md`、`cases/<id>/prompt.md`。`variants/baseline/` 完整拷贝被测目录，实验组从副本改动。Skill 与任务仓库分开，真实仓库配置见 [coding.md](coding.md)。源版本后续有变化，先刷新对应副本，缓存才会看到变化。
3. 检查任务命令如何提供用量，能获取的接入 `${trial_out}/usage.json`；找不到则说明未知。沿用已确认的登录和工具链，不随意切换模型、身份或任务约束。
4. **提前准备排查材料**：stdout/stderr 和调用输入自动保存；任务额外文件声明为 `evidence.files`。需要以后重跑工作区评分脚本时保存完整工作区。检查当前 CLI / 包装脚本能否把本次工具调用、错误和子任务记录导出到 `${trial_out}`，用 `trace.files` 声明。没有导出能力时提前说明只能核查输入输出，不能还原内部过程。轨迹是可选能力，不读取无关全局会话。配置见 [execution-audit.md](execution-audit.md)。
5. 标准确认后执行 `brief --confirm-criteria`，退出 0 再 `run --gate`。用户只想比较暂不判断能否采用时去掉 `--gate`。最后执行 `report`，按 SKILL.md 的汇报要求主动解释并提供审计入口。

## 复用和异常

已有匹配执行与评分时默认复用，不重新跑对照组。只换评分使用 `rescore` 或匹配缓存的 `run`；只有用户明确要重新执行时才使用 `--force` / `--no-reuse`。`--only-*` 只选择指定范围，不自动补对照组。详细规则见 [lifecycle.md](lifecycle.md)。

`brief` 退出 2：读错误码，修配置或补缺失事实，不向用户丢调用栈。`run --gate` 退出 1：解释具体不满足项。退出 3：检查是否达到明确设置的上限、未登录、工作区不受信任、模型/参数不可用等；实验未完成，不能当作改法失败。`brief` 通过仅代表配置检查通过，不保证外部命令已能执行。

结论必须来自保存的结果。需要新实验验证某个原因时说明最小验证和调用范围，沿用已有授权；不要为了补报告偷偷重跑。结束和清理按 [storage.md](storage.md) 执行。
