# AgentLab

对象是已经存在的目录（Skill 或自己写的工作流），不是从零新建一个 skill。分数只认 `run` 写下来的结果。不要让用户去翻 yaml 或自己敲命令。

先分清他要的是哪条路，不要两条一起上。

## 先分清路

**商量怎么改**（优化、改 prompt、降时间或花费、别漏事实）：先只谈改法。读目录，拿出一版优化方案，和他来回改，直到他说就按这个改。这之前不要问命令怎么跑、不要写实验计划、不要 `brief` / `run`。

**直接测**（测这个目录、同一个版本跑几次看稳不稳、对比两个已经存在的版本）：跳过改法讨论，也不要发明一处改动。从「实验计划」起头。

说不清时按「商量怎么改」走，并在开头用一句话说明你的判断，让他改口。

## 优化方案

只在「商量怎么改」这条路上用。给用户的第一条回复先写这个，单独成段：

- 改哪里（哪个文件、哪一段）
- 具体怎么改
- 为什么这能改善他在乎的点
- 可能变差或漏掉什么

不要只重复他的目标。没有把握也先给一版，让他改。他指定了改法就用他的。一次只谈这一处。

他点头「就按这个改」之前，停在讨论里。点头之后再进入实验计划，把谈妥的改法当作对照里的新版本。

## 实验计划

「直接测」时作为第一条回复的开头；「商量怎么改」时等改法谈妥后再写。同一条回复里写清怎么测，不要先问一轮再另发计划。

先用这张表。没有改动的那一版永远叫对照组，不要叫实验组1。谈妥的改法从实验组1起编：一处改法就是对照组 + 实验组1，再多一处加实验组2。不要说变体、格子。数字要填死；还没定的标成「未定」，不要用乘法口算代替这张表：

```text
| | 对照组 | 实验组1 | 实验组2 |
|---|---|---|---|
| 是什么 | <现在的目录 / 现成版本> | <第一处改法> | <第二处改法；没有则本列不写> |
| 跑什么 | <N> 个用例 × 各 <R> 次 | 同样 | 同样 |
| 这次跑几次 | <N×R> 或 0（用已存基线） | <N×R> | <N×R> |

这次新跑 <本次次数> 个试验。组数 = 表头有几列。

并发 <K>：同一时刻最多 <K> 个试验在跑，其余排队。
不是对照组和实验组成对一起跑。先开的往往是同一用例、对照组里还要新跑的那几个。
```

只有一处改法时不要空着实验组2，直接去掉那一列。只测一个现成版本、没有改法时只留对照组。

对照组不必每次重跑。同一实验里已经有完整基线、且看的标准和用例没变时，对照组「这次跑几次」写 `0（用已存基线）`，只跑实验组。换了实验目录、或改了关注点/用例，基线作废，对照组要重跑。用户说重跑对照组才重跑。

表后面再补：看哪些标准、必须满足哪几条（不满足就不能用）、产物放哪。默认不设墙钟、金额或 token 上限。跑测试的人自己清楚消耗；硬上限只会把还在跑的试验掐掉。用户没要求就不要写 `wall_clock_s` / `usd` / `tokens`，也不要自己估一个。只有他主动要求时才写进契约。写进契约的次数和并发用草稿里的 `repetitions` / `max_parallel`，不要另编一套数字。

没有用户确认（或回复里明确改计划）之前，不要 `run`。`brief` 可以在他确认后立刻做。

## 规模与并行（计划里必须写明）

外搜、真 CLI、LLM 裁判这类有噪声的对照：**不要默认 1 个用例 × 1 次重复**。默认提案是 **至少 3 次重复**（同一用例），或 **至少 2 个用例且各重复 ≥2**。确定性假 command 才可以用 1×1。

能并行就并行（同时最多 2～4 个试验）。只有用户要求、或会抢同一登录/额度时才改成串行，并在计划里写原因。

用户可以说「再多跑几次」或「这次先试 1 次」；按他的话改 `repetitions` / 用例数后再跑。

## 对用户（实验阶段才问）

进入实验计划之后，只补还缺的事实：测哪个目录、本机哪条已经能登录使用的命令、任务说明怎么喂给这条命令（默认从标准输入读；用户没确认不要猜是哪条命令）。交易向目录还要问的见 `references/trading.md`。对用户不要说「夹具」。这些问句跟在实验计划后面；改法还没谈完时不要问。不要把预算当成必问题，默认不设上限。

改动会拷到这次试验自己的目录里再跑，不会装进他的全局 skills。确认标准时用几句话复述「看什么、哪几条必须满足」。不要让他打开或编辑 yaml。

讲结果时对人说：看过的每一条里，哪一点满足、哪一点不满足，所以这版能不能用。不要说门禁、格子。不要甩文件清单当作业。

## 定位本 skill 和 Python

`SKILL.md` 所在目录就是 skill 目录。CLI 是 `scripts/cli.py`。先解析出绝对路径，不要把占位符当字面量留下。

解释器**默认自己解决**，不要为这个问用户。执行：

```text
<任意本机 python3> <skill-dir>/scripts/ensure_python.py
```

stdout 第一行就是要用的解释器（3.11+，已能 import pydantic / yaml）。脚本会：先用已就绪的 `AGENTLAB_PYTHON` / `python3.12` / `python3.11` / 合格的 `python3`；都不行就在 `~/.agentlab/.venv`（或 `$AGENTLAB_HOME/.venv`）建隔离环境并只往那里装依赖。**禁止**对系统 Python 执行 `pip install`。

只有 `ensure_python.py` 退出非 0（机器上没有 3.11+）时，才问用户从哪装一个 3.11+。用户若主动指定 venv，设 `AGENTLAB_PYTHON` 后再跑同一脚本。

之后一律：

```text
<py> <skill-dir>/scripts/cli.py brief --exp <实验目录> --confirm-criteria
<py> <skill-dir>/scripts/cli.py run --exp <实验目录> --gate
<py> <skill-dir>/scripts/cli.py report --exp <实验目录>
```

不要让用户去装全局 `agentlab`，也不要假设 PATH 里有它。

## 你自己做

契约字段见 `references/contract.md`。只在改法谈妥、或用户一上来就要测、且实验计划已确认之后，在实验目录里写齐这些再跑 `brief`：

- `experiment.yaml`（按契约草稿，含其中的 repetitions / max_parallel / max_trials；不要擅自加上墙钟或金额上限）
- `criteria.md`（按关注点分节）
- `cases/<id>/prompt.md`
- `variants/baseline/`：源目录完整拷贝
- 有谈妥的改法时：`variants/<treatment-id>/` 再拷一份 baseline，只在副本上改，不要改用户的源目录。只测一个现成版本时不要编 treatment

新实验目录：默认 `$AGENTLAB_HOME/experiments/<id>/`（未设 `AGENTLAB_HOME` 则为 `~/.agentlab/experiments/<id>/`）。用户指定了目录才写到别处。已有同名且已是本实验则接着用；撞车则 `<id>-2`。

用户确认命令之后、开跑之前：自己在本机找这条命令把用量记在哪，接到这次试验的分数上。找不到就说找不到，不要编。

产物写试验自己的目录；取数、登录、本机已经能用的工具链要沿用，不要只建一个空家目录导致取不到数。

用户确认后跑 `brief --confirm-criteria`。退出 0 再 `run --gate`（他说这次只比较、先不判断能不能用，就去掉 `--gate`）。对照组已有完整结果且口径没变时不要重跑，runner 会跳过；用户要重跑对照组时加 `--force`。跑完 `report`，读 `report.md` / `promotion.json`，按关注点讲。不要自己编分数。

`brief` 退出 2：读错误码，你改契约或再问缺的那一项，不要把栈甩给用户。`run --gate` 退出 1：说明哪一点不满足、所以这版不能用。退出 3：你设了上限并且到了、实验没跑完。

目录像交易/研报 Skill（产物在 `$SCUTIO_HOME/cache/trading`、报告有方向和动作）时，再读 `references/trading.md`。其它目录不要套那份关注点。

## 禁止

- 自己执行 `git worktree add`（要比工作区改动时在契约里写 `isolation.type: git-worktree`，由 runner 建沙盒）
- 写用户全局 skill 目录（`~/.claude/skills` 等）
- 为了打分去 exec 被测 command
- 跳过 brief 宣称可跑
- 擅自给试验加墙钟、金额或 token 上限
- 改法还没谈完就问怎么跑、写实验计划或开跑
- 实验计划不写清对照组/实验组各是什么、一共几次、并发时谁和谁一起跑
- 计划未讲清规模/并行就开跑
- 自动一轮轮改目录刷分；他说再试一处时最多加 1 个 treatment，再走 brief + run
